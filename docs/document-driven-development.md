# Image Partners 문서 기반 개발 규칙

> 상태: 기준
> 적용 대상: 사람 개발자, Codex 및 그 밖의 개발·운영 에이전트
> 기준일: 2026-08-05

## 1. 목적

모든 변경은 먼저 기존 시스템 정의와의 관계를 설명하고, 구현·테스트·문서·운영 근거를 함께 갱신한다. 에이전트가 바뀌어도 같은 용어, 상태 모델, 권한 경계와 배포 기준으로 판단하는 것이 목적이다.

문서가 코드를 대신하지는 않는다. 코드나 운영 동작이 문서와 다르면 어느 쪽도 임의로 정답으로 간주하지 않고, 실제 동작과 사업 의도를 확인해 불일치를 결함 또는 의사결정 과제로 기록한다.

## 2. 문서의 우선순위와 역할

1. `docs/system-definition.md`: 서비스 범위, 행위자, 핵심 흐름, 데이터, 권한, 외부 연동의 승인 기준
2. 도메인 기준 문서: 이미지 상태, 용어, 운영정책, 모니터링처럼 상세 불변조건을 정의
3. Supabase 마이그레이션과 테스트: 데이터 구조·RLS·회귀 조건의 실행 가능한 근거
4. 작업 명세와 계획: 승인된 변경의 목적, 범위, 수용 기준
5. 운영 백로그와 배포 기록: 미완료 위험과 실제 검증 증거

과거 계획 문서는 현재 상태의 근거가 아니다. 현재 기준 문서와 충돌하면 새 작업에서 정리한다.

## 3. 변경 절차

### 3.1 변경 등록

작업을 시작할 때 다음을 짧게 정의한다.

- 문제와 사용자·사업 영향
- 대상 행위자와 화면/API
- 현재 동작과 원하는 동작
- 데이터·권한·보안·개인정보·법적 고지 영향
- 기능 플래그와 공개 범위
- 성공 조건과 실패·롤백 조건

요구가 불분명해 결과가 크게 달라질 때만 결정을 요청한다. 안전한 범위의 가정은 작업 기록에 명시한다.

### 3.2 영향 분석

아래 항목 중 해당하는 것을 코드 수정 전에 확인한다.

| 변경 영역 | 반드시 확인할 기준 |
| --- | --- |
| 화면 문구·상태명 | `service-terminology.md`, 한국어·영어 사전, 이메일·약관 동시 영향 |
| 이미지 업로드·검토·삭제 | `image-state-visibility.md`, 사진작가·관리자·구매자 세 화면, 장바구니·주문 이력 |
| 인증·권한 | Supabase RLS, 서버 권한 검사, 비로그인·일반·사진작가·관리자 거부 테스트 |
| 주문·결제·다운로드 | 기능 플래그, 주문 상태, 입금 승인, 계약 고지, 기존 주문 스냅샷 |
| 개인정보·외부 서비스 | 개인정보처리방침, 국외 이전, 보유·파기, 비밀값 관리 |
| DB·스토리지 | 순방향 마이그레이션, RLS, 기존 데이터 보정, 참조 무결성, 복구 방법 |
| 배치·모니터링 | 중복 실행 안전성, 인증, 최신 실행 증거, 실패 알림, 운영 런북 |
| 배포 설정 | CI, 환경별 값, Vercel/Supabase 대상, 배포 후 스모크와 롤백 |

### 3.3 명세와 구현

- 복수 화면이나 상태 전이가 바뀌는 기능은 구현 전에 `docs/superpowers/specs` 또는 작업 문서에 흐름과 수용 기준을 기록한다.
- DB 변경은 새 순방향 마이그레이션으로만 수행한다. 이미 적용된 운영 마이그레이션을 고쳐 쓰지 않는다.
- 공개되지 않은 기능은 UI만 숨기지 않고 서버에서도 기능 플래그와 권한으로 차단한다.
- 비공개 원본은 공개 URL로 만들지 않는다. 접근은 서버가 권한을 확인한 뒤 제한된 방식으로 제공한다.
- 사용자 용어는 `service-terminology.md`를 따르며 내부 영문 상태값과 사용자 표시명을 구분한다.

### 3.4 검증

변경 위험에 맞는 테스트를 추가하고 최소한 다음 게이트를 통과한다.

```bash
npm audit --omit=dev --audit-level=high
npm run typecheck
npm run lint
npm test
npm run build
```

DB 마이그레이션이 있으면 새 로컬 DB 적용과 `supabase db lint --local --level error`를 추가한다. 인증·주문·업로드·삭제처럼 다중 역할 흐름은 API 단위 테스트만으로 완료하지 않고 역할별 E2E 또는 재현 가능한 운영 스모크 근거를 남긴다.

### 3.5 문서와 배포

같은 변경에서 다음을 갱신한다.

- 시스템의 범위·흐름·연동·권한이 바뀌면 `system-definition.md`
- 도메인 불변조건이 바뀌면 해당 기준 문서
- 남은 위험이나 외부 결정이 있으면 `operations-backlog.md`
- 운영 절차나 경보가 바뀌면 런북·모니터링 문서
- 사용자 고지가 바뀌면 화면, 이메일, 약관·개인정보처리방침의 일관성

배포는 [운영 배포 인수인계](./production-deployment-handoff.md)의 검증과 롤백 기준을 따른다. 문서에 “완료”라고 쓰는 시점은 코드 작성 시점이 아니라 테스트와 필요한 운영 반영까지 검증한 뒤다.

## 4. 완료 조건(Definition of Done)

다음이 모두 충족돼야 변경을 완료로 본다.

- 승인된 요구와 수용 기준을 충족한다.
- 허용·거부 권한 경로와 주요 실패 경로가 검증됐다.
- 기존 데이터와 화면 상태 전이에 모순이 없다.
- 보안·개인정보·법적 고지 영향이 반영됐거나 해당 없음이 확인됐다.
- 자동 테스트, 타입 검사, 린트, 빌드와 필요한 E2E가 통과했다.
- 시스템 정의서와 관련 기준 문서가 현재 동작과 일치한다.
- 배포 대상·커밋·마이그레이션을 재현할 수 있다.
- 배포 후 핵심 경로를 확인했고 남은 위험은 백로그에 기록했다.

## 5. 에이전트 작업 시작 체크리스트

1. `AGENTS.md`, 시스템 정의서, 이 문서와 해당 도메인 문서를 읽는다.
2. `git status --short`로 사용자 변경을 확인하고 보존한다.
3. 현재 코드, 최신 마이그레이션, 테스트와 운영 백로그를 대조한다.
4. 작업 범위와 문서 영향 목록을 만든다.
5. 구현 뒤 검증 결과와 아직 확인하지 못한 사실을 구분해 보고한다.

에이전트는 과거 대화나 계획 문서만으로 운영 상태를 단정하지 않는다. 운영 상태는 헬스체크, 배포 ID, CI 실행, DB 마이그레이션 목록처럼 재검증 가능한 증거로 판단한다.

## 6. 정기 유지보수와의 연결

3일 주기 점검은 시스템 정의서의 구성요소와 비기능 기준을 체크리스트로 사용한다. 자동화는 조회·검사·보고·PR 준비까지 담당하고, 광범위한 자동 수정과 운영 배포는 승인 게이트 뒤에 둔다.

점검 결과는 다음 중 하나로 분류한다.

- `P0 오픈 차단`: 보안, 데이터 손실, 법정 필수 고지, 핵심 거래 불능
- `P1 오픈 전 권장`: 장애 탐지·복구, 주요 E2E, 배포 통제, 성능 용량
- `P2 후속 개선`: 비용 최적화, 사용성 고도화, 아직 비공개인 기능
- `관찰`: 현재 정상이나 수치·실행 최신성을 계속 확인할 항목

동일 문제가 해결되지 않은 채 반복되면 새 항목을 계속 만들지 않고 기존 백로그나 이슈에 증거를 누적한다.
