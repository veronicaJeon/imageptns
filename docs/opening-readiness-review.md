## P0 — 정식 공개 전에 완료

### P0-1. 사업자 공시와 주문 계약 고지

현재 `/business-info`는 “공시사항을 준비하고 있습니다”로 표시되고 대표자명, 사업자등록번호, 공개 전화번호와 통신판매업 확인정보가 공개되지 않는다. 반면 계좌이체 주문 API는 공시 완료 여부와 관계없이 접근 가능하다.

완료 기준:

- 관리자 공시사항에 실제 값을 입력하고 공개한다.
- 통신판매업 신고번호·신고기관 또는 적용 예외 여부를 사업자 판단과 필요한 자문으로 확정한다.
- 주문 확정 전에 상호·대표자·주소·전화·이메일, 가격과 VAT, 제공 시점, 취소·환불, 증빙, 라이선스 핵심 조건으로 연결한다.
- 구매자가 주문 조건과 디지털 콘텐츠 제공 후 청약철회 제한을 확인·동의하고 버전·시각을 주문 스냅샷으로 보존한다.
- 공시가 불완전하면 유료 계좌이체 주문 생성을 서버에서 거부하되 무료 사용권은 유지한다.
- 구매자에게 주문내용을 이메일 또는 다운로드 가능한 전자문서로 교부한다.

전자상거래법 제13조는 통신판매 청약을 위한 표시·광고에 상호·대표자, 주소·전화·이메일, 신고 확인정보를 포함하고 계약 전 거래조건을 고지하도록 정한다. 실제 적용 범위와 문구는 공개 전에 국내 법률·세무 전문가 검토를 권장한다.

### P0-2. 계좌이체 주문 신뢰성·알림·E2E

완료. 마이그레이션 065~067과 앱 변경으로 주문·항목·정책 스냅샷의 원자 생성, idempotency, 접수·승인·취소 이메일 outbox, 관리자 재전송과 클라이언트 직접 주문 생성을 차단했다. 2026-08-05 운영에서 임시 구매자·관리자로 주문 재시도, 접수 메일 2종, 승인·취소 메일, 다운로드 권한과 원본 파일을 확인한 뒤 주문·계정을 정리했다. 단건·일괄 다운로드와 구매자 주문이력은 강화된 회귀 스크립트에서 계속 검사한다.

완료 기준:

- 주문, 주문 항목, 가격·라이선스·정산 스냅샷을 하나의 DB 트랜잭션/RPC로 생성한다.
- 동일 요청의 중복 주문을 막는 idempotency key와 재시도 규칙을 둔다.
- 요청 접수 시 구매자에게 주문번호·금액·계좌·기한·정책 링크를 보내고 운영자에게 알린다.
- 승인·취소 시 구매자에게 상태와 다운로드/문의 동선을 보낸다. 메일 실패가 주문 상태를 되돌리지는 않되 재전송 대상과 실패를 기록한다.
- 임시 구매자·관리자 계정으로 유료 주문 생성 → 관리자 승인 → DB trigger 다운로드 생성 → 단건/일괄 다운로드 → 주문 이력까지 운영 E2E를 수행하고 데이터를 정리한다.
- 무료 사용권, 삭제·공개 중지 이미지, 중복 승인, 잘못된 금액·라이선스의 거부 경로도 회귀한다.

### P0-3. 백업 복구 훈련

백업이 존재한다는 가정만 있고 격리 프로젝트에서 실제 복구한 증거와 목표 복구시간(RTO)·허용 데이터 손실(RPO)이 없다. DB가 복구돼도 Storage 객체와 이미지·주문 스냅샷 참조가 맞는지 검증해야 한다.

완료 기준:

- 운영과 분리된 Supabase 프로젝트/버킷에 승인된 복구 시점을 복원한다.
- 계정 프로필, 공개 이미지, 원본·미리보기 참조, 주문·다운로드·정산, 정책 문서의 표본 무결성을 검사한다.
- Storage 백업 범위와 복구 방법을 확인하고 DB-only 복구 한계를 문서화한다.
- 측정된 RTO/RPO, 담당자, 비밀값 복구, DNS/Vercel 전환과 원복 절차를 런북에 기록한다.
- 운영 원본을 덮어쓰지 않고 훈련 데이터를 정리한다.

### P0-4. 변경·배포 통제

CI와 수동 배포 워크플로는 존재하지만 main 보호가 확인되지 않고, 여러 에이전트가 동시에 작업할 때 문서·테스트 없이 직접 main에 반영될 여지가 있다.

완료 기준:

- main에 직접 push를 제한하고 필수 `Test, Build & Security`, `Database Migrations` 체크를 설정한다.
- 최소 1회의 승인 또는 저장소 소유자 승인 규칙과 대화 해결 조건을 둔다.
- Production GitHub Environment에 승인자를 두고 배포 워크플로의 허용 branch/SHA를 검사한다.
- DB 마이그레이션 릴리스와 앱 배포 순서, 롤백 불가능 마이그레이션의 대응을 PR 템플릿에서 확인한다.
- 모든 에이전트가 `AGENTS.md`, 시스템 정의서와 문서 기반 개발 규칙을 읽고 같은 변경에서 문서를 갱신한다.

## 3일 유지보수 배치 제안

2026-08-06 기준 72시간 유지보수 워크플로를 활성화했다. 첫 전체 실행과 단일 추적 이슈 보고, 성공 후 72시간 이내 실행 건너뛰기를 확인했다. 아래 내용은 현재 운영 기준이다.

정기 루틴은 “자동으로 무엇이든 고치고 바로 운영 배포”가 아니라 “자동 점검 → 문서화된 판정 → 작은 PR → 승인 → 검증 배포”로 구성한다. 이상이 없으면 배포하지 않는다. 보안사고·장애·법적 차단 문제는 3일을 기다리지 않고 즉시 대응한다.

정확한 72시간 주기는 월 경계에서 어긋나는 `*/3` cron 대신 GitHub Actions를 매일 실행하고 마지막 성공한 유지보수 이슈/실행으로부터 72시간이 지났을 때만 본 작업을 수행하는 방식을 권장한다.

### 배치 단계

1. **기준 확인**: 시스템 정의서 버전, 운영 배포 SHA, 마이그레이션, 기능 플래그의 차이를 수집한다.
2. **자동 점검**: audit, typecheck, lint, test, build, fresh DB migration lint, health, 공개 경로 smoke, AI·자동파기 최신성, GitHub CI·보호 설정, 공시 공개 상태를 검사한다.
3. **판정·기록**: P0/P1/P2/관찰로 분류하고 기존 이슈와 백로그에 증거를 누적한다. 중복 이슈는 만들지 않는다.
4. **수정 PR**: 하나의 원인과 작은 범위로 branch/PR을 만들고 수용 기준·위험·문서 변경·롤백을 포함한다. 법률 문구, 환경값, 데이터 삭제는 자동 변경하지 않는다.
5. **승인·검증**: Preview/격리 DB에서 E2E하고 사람이 diff와 공개 영향을 승인한다.
6. **운영 배포**: 승인된 PR만 배포한 뒤 health·핵심 경로·관련 E2E를 확인한다. 실패 시 배포를 완료로 표시하지 않는다.
7. **기준 갱신**: 시스템 정의서, 도메인 문서, 운영 백로그와 배포 증거를 같은 작업에서 갱신한다.

### 자동화 가능 범위

- 안전한 자동 수행: 조회, 정적 검사, 테스트, health/smoke, 보고서·이슈 갱신, PR 초안
- 조건부 자동 수정: 형식·문서 링크·명확한 저위험 회귀처럼 테스트로 결과가 고정되는 작은 변경
- 사람 승인 필수: 운영 배포, DB 마이그레이션, 환경변수, 법률·가격·환불 정책, 권한 확대, 데이터 파기, 의존성 major 변경
