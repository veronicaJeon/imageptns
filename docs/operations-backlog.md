# 운영 잔여 과제

이 문서는 현재 진행을 막지 않지만 운영 안정성을 위해 다시 확인해야 하는 항목을 추적한다. 완료 항목은 삭제하지 않고 상태와 검증 근거를 갱신한다.

## 2주차 잔여

| 상태 | 과제 | 완료 기준 |
| --- | --- | --- |
| 운영 확인 대기 | 첫 정기 자동파기 실행 | `data_retention_runs`에 운영 cron의 실제 실행 성공 기록이 남는다. |
| 운영 확인 대기 | 매일 Mistral 합성 진단 | `operational_events`에 `ai_synthetic_check=ok`가 정기적으로 누적된다. |
| 계정 필요 | 미승인·승인 사진가 운영 E2E | 미승인 계정은 403, 승인 계정은 정상 메타데이터, 쿼터 초과는 429를 운영 세션에서 확인한다. |
| 별도 훈련 | Supabase 백업 복구 | 격리된 테스트 프로젝트에 백업을 복원하고 핵심 테이블·스토리지 참조를 검증한다. 운영 DB에는 복구 훈련을 직접 수행하지 않는다. |
| 정책 결정 | Mistral 장애 대체 공급자 | 후보 모델의 품질·비용·국외이전·보유정책을 비교하고 회로차단 후 수동 입력 또는 대체 API 전환 기준을 확정한다. |

## 후속 고도화

| 우선순위 | 과제 | 착수 조건 |
| --- | --- | --- |
| 높음 | 전용 uptime/APM 및 호출 알림 | 유료 서비스 공개 또는 GitHub 모니터가 운영 요구를 충족하지 못할 때 |
| 높음 | AI 작업 대기열·재시도·회로차단 | 업로드 동시 처리량 증가 또는 공급자 장애가 반복될 때 |
| 중간 | ELK 기반 감사 로그 | 이벤트 스키마, 개인정보 마스킹, 접근권한과 보존기간을 승인한 뒤 |
| 중간 | 스토리지 실패율 세분화 | 업로드·다운로드 API별 운영 이벤트 계측을 확대할 때 |
| 낮음 | 내부 비전 LLM 검증 | 외부 API 비용·데이터 정책·처리량이 자체 운영 비용을 정당화할 때 |
